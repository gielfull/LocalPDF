# Contributing to LocalPDF

Thanks for helping. This guide covers getting set up, what's expected in a change, and the
few rules that can't bend.

## Get set up

You need macOS 27, Xcode 27 and XcodeGen (`brew install xcodegen`).

```bash
git clone https://github.com/gielfull/LocalPDF.git
cd LocalPDF
xcodegen generate          # the .xcodeproj is generated, never committed
open LocalPDF.xcodeproj
```

In Xcode, pick your own team under *Signing & Capabilities* (or build from the terminal with
`CODE_SIGN_IDENTITY=- DEVELOPMENT_TEAM=` for ad-hoc signing). Don't commit your team ID.

Run everything from the terminal:

```bash
# All tests (app + engine)
xcodebuild -project LocalPDF.xcodeproj -scheme LocalPDF -destination 'platform=macOS' \
  -derivedDataPath build/DerivedData CODE_SIGN_IDENTITY=- DEVELOPMENT_TEAM= test

# Just the engine, fast
(cd Packages/PDFEngine && swift test)
```

The Debug build is a separate app called **LocalPDF Dev**, so it never collides with an
installed copy.

## Find your way around

```
project.yml                     the Xcode project, generated by XcodeGen
Sources/LocalPDF/
├── App/                        app entry point, windows, sidebar, Finder Quick Actions
├── Features/<Tool>/            one folder per tool: its options UI
├── Features/ToolRunner/        shared tool screen, job queue, result sheet
└── DesignSystem/               tiles, cards, thumbnails, glass components
Packages/PDFEngine/             every tool's logic, as a Swift package with no UI code
├── Sources/PDFEngine/Core/     the contract: ToolID, ToolCatalog, PDFOperation, errors
├── Sources/PDFEngine/<Area>/   Organize, Optimize, Convert, Edit, Security operations
├── Sources/CQPDF, CJPEG/       vendored qpdf and libjpeg (don't edit)
└── Tests/PDFEngineTests/       engine tests
Tests/LocalPDFTests/            app tests
```

- The `.xcodeproj` is generated: edit `project.yml` and run `xcodegen generate`, never the
  project itself. `Info.plist` and the entitlements file are generated from `project.yml` too.
- The app target is `MainActor` by default; `PDFEngine` is deliberately nonisolated and
  `Sendable` so jobs run off the main actor.

## Rules that can't bend

1. **No network access, ever.** Never add `com.apple.security.network.client`/`.server` or
   enable outgoing connections. "Your files never leave your Mac" is the product. A feature
   that needs the network is out of scope.
2. **PDFEngine has no UI imports.** No SwiftUI or AppKit in `Packages/PDFEngine`; it has to
   run from a future background worker and command-line tool.
3. **Never modify the user's files in place.** Operations write to a temporary directory and
   the app moves the results.
4. **Don't edit vendored code.** `Sources/CQPDF` (qpdf) and `Sources/CJPEG` (libjpeg) are
   upstream releases re-created by `Packages/PDFEngine/Scripts/vendor-qpdf.sh`.
5. **On-device AI only.** Apple's on-device model, never a cloud model or Private Cloud
   Compute.

## Making a change

- **Open pull requests against `main`.** For anything bigger than a small fix, open an
  issue first so we can agree on the approach before you spend time on it.
- **Adding a tool:** implement a `PDFOperation` in `Packages/PDFEngine/Sources/PDFEngine/<Area>/`,
  its options UI in `Sources/LocalPDF/Features/<Tool>/`, wire it into `ToolInspector` and
  `ToolSession+Request`, then add its `ToolID` to `implemented` in `ToolCatalog`.
- **Tests are part of the change.** We use Swift Testing (`@Test`, `#expect`). Generate
  fixture PDFs in code; don't commit binary PDFs. A test should be able to fail for the right
  reason.
- **Swift 6 with complete concurrency checking.** No warnings in new code.
- **Match the surrounding style.** Comments explain *why*, not *what*.
- **UI changes:** include a before/after screenshot in the pull request, made with harmless
  sample files.

## Pull requests

- Keep each PR focused on one thing.
- Make sure `xcodebuild … test` passes locally. CI builds and tests every PR on GitHub's
  Xcode 27 runner too.
- Describe what changed and how you checked it.
